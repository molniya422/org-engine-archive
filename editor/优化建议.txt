# Org Engine Editor 深度分析与改进建议

## 一、项目现状全景

### 1.1 整体架构

```
┌─────────────────────────────────────────────────────┐
│                    Electron 壳层                      │
│  (主进程 + preload + IPC 桥接)                       │
├─────────────────────────────────────────────────────┤
│                   前端 (React)                       │
│  React Flow 画布 · Radix UI · Lucide 图标 · Tailwind │
│  路由: / → /studio/:orgId → /studio/:orgId/runs/:id │
├─────────────────────────────────────────────────────┤
│              后端服务器 (Fastify)                     │
│  REST API + WebSocket + MCP Server                   │
│  Org CRUD · Skill 扫描 · Playbook · Template · Run  │
├─────────────────────────────────────────────────────┤
│          编排引擎 (Python 子进程)                     │
│  orchestrator-adapter · JSON-RPC 2.0 (stdio)        │
│  实际执行多智能体工作流                                │
└─────────────────────────────────────────────────────┘
```

### 1.2 核心数据模型

| 层级 | 概念 | 关键属性 |
|------|------|---------|
| **组织层** | OrgConfig | name, departments[], contracts[], budget{}, skill_paths[] |
| **部门层** | Department | name, roles[], manager_pipeline[], required |
| **角色层** | Role | name, agentType, bound_skill, can_veto, can_escalate, parallel_with[] |
| **管理层** | ManagerStage | decompose / dispatch / collect / review |
| **契约层** | Contract | key, owner_dept, version, schema, dependents[] |
| **预算层** | Budget | max_depth, max_cycles_per_layer, max_parallel_agents, gateway_timeout |

### 1.3 已实现功能清单

- ✅ **组织配置管理**：YAML 存储、CRUD、Schema 验证、导入导出
- ✅ **可视化编辑器**：React Flow 画布、节点拖拽
- ✅ **部门/角色管理**：层级结构、Agent 类型绑定、Skill 绑定
- ✅ **Manager Pipeline**：部门级四阶段流水线（分解→分发→收集→评审）
- ✅ **Skill 系统**：文件系统扫描、内置 Agent 类型池
- ✅ **Playbook**：可复用工作流模板，支持 stages + graph
- ✅ **Template**：用户自定义模板
- ✅ **运行管理**：启动/取消/查询、WebSocket 实时日志、人类在环（decision）
- ✅ **MCP 协议**：内置 MCP stdio 服务器，9 个工具
- ✅ **预算控制**：深度、循环数、并行数、超时限制
- ✅ **部门契约**：跨部门接口定义

## 二、核心优势（对比主流项目）

### 2.1 组织化思维最彻底

**对比 CrewAI / MetaGPT**：
- CrewAI 只有「角色-任务-Crew」三层，缺少部门层级概念
- MetaGPT 是固定的软件公司流程，不可定制
- **你的优势**：Org → Department → Role 的三级组织模型，加上 Manager Pipeline 和 Contract，最贴近真实公司的运作方式，用户心智负担最低

### 2.2 Manager Pipeline 设计独特

**对比所有项目**：
- 其他框架要么是扁平的角色协作，要么是固定的流程
- **你的优势**：每个部门都有独立的 manager_pipeline（decompose→dispatch→collect→review），把"部门管理者"的职责显式化了，这是非常有洞察力的设计

### 2.3 Contract 机制有创新性

**对比所有项目**：
- 其他框架缺少部门间协作的接口定义
- **你的优势**：Contract 定义了部门间的输入输出契约（schema + version + dependents），解决了大规模组织中"部门间如何协作"的问题，类似微服务的 API 契约

### 2.4 Budget 系统实用

**对比 LangGraph / AutoGen**：
- 其他框架的资源控制比较原始（通常是全局的 max_steps）
- **你的优势**：Budget 是分层的（max_depth / max_cycles_per_layer / max_parallel_agents），更精细，也更符合"公司预算"的隐喻

### 2.5 MCP 原生支持

**对比所有项目**：
- 大部分框架的工具接入是自定义格式
- **你的优势**：原生支持 MCP 协议，直接对接 MCP 生态，工具接入标准化

## 三、关键差距与改进建议

### 🔴 P0：核心能力短板

#### 1. 编排引擎黑盒化，可观测性不足

**现状**：
- 编排逻辑在 Python 子进程中，Node.js 端只做 JSON-RPC 转发
- 前端只能看到日志，看不到内部状态

**对比**：
- LangGraph：每个节点的状态、输入输出、检查点都可查询
- LangSmith/Langfuse：完整的 Trace 可视化

**改进建议**：
- **增加运行时状态 API**：暴露每个 Agent 的当前状态、输入输出、token 消耗、耗时
- **前端运行可视化**：在画布上实时高亮当前执行的节点，展示消息流向
- **Trace 视图**：新增时间线视图，展示完整的调用链和每个步骤的详情
- **检查点支持**：支持运行中断后恢复，支持回退到某个检查点

#### 2. 拓扑模式单一，缺少灵活性

**现状**：
- 目前是严格的层级式（树状）组织
- 协作模式固定（manager pipeline + 角色执行）

**对比**：
- Agentic Titan：9 种协作拓扑（层级、网状、环形、星形等）
- AutoGen：群聊模式，动态协商
- CrewAI：顺序、层级、并发三种模式

**改进建议**：
- **增加"项目组"概念**：支持跨部门的临时团队（矩阵式组织）
- **支持网状协作**：角色之间可以直接通信，不一定要经过 manager
- **动态拓扑切换**：同一组织可以配置多种协作模式，按任务类型切换
- **群聊模式**：增加类似 AutoGen 的群聊协商模式，用于探索性任务

#### 3. 缺少自然语言编排能力

**现状**：
- 纯可视化拖拽配置，门槛较高

**对比**：
- MASFactory：Vibe Graphing，自然语言三步生成完整编排
- Flowise：模板化快速搭建

**改进建议**：
- **自然语言生成组织**：用户输入"帮我创建一个内容创作团队，有主编、文案、设计、运营"，自动生成完整的部门-角色-技能配置
- **自然语言调整**："给设计部加一个评审岗"、"把文案和设计改成并行"
- **智能推荐**：根据任务描述推荐合适的组织架构和 Skill
- **对话式编辑**：侧边栏增加 AI 助手，边聊边改

### 🟡 P1：体验与生态

#### 4. Skill 系统较初级

**现状**：
- 从文件系统扫描 Markdown 文件
- 只有 name + description，缺少版本、分类、输入输出 schema

**对比**：
- MCP：完整的工具发现、调用、schema 验证
- CrewAI：Tool 类有完整的输入输出定义

**改进建议**：
- **Skill 元数据增强**：增加版本号、作者、标签、分类、图标
- **输入输出 Schema**：每个 Skill 定义明确的输入参数和返回值 schema，支持自动验证
- **Skill 组合**：支持 Macro Skill（由多个子 Skill 组合而成）
- **Skill 市场**：内置模板市场，支持一键安装社区 Skill
- **Skill 测试**：支持单独测试某个 Skill

#### 5. 前端交互不够丰富

**现状**：
- 基础的 React Flow 画布
- 只有 3 个路由页面

**对比**：
- Langflow：左侧组件库 + 中间画布 + 右侧属性面板的经典三段式
- Flowise：模板市场、拖拽、实时预览、调试面板

**改进建议**：
- **三段式布局**：左侧组件库（部门、角色、Skill 可拖拽）+ 中间画布 + 右侧属性面板
- **多视图切换**：
  - 组织架构图（树状，展示汇报关系）
  - 流程图（DAG，展示任务流转）
  - 列表视图（表格形式，适合批量编辑）
- **画布增强**：迷你地图、缩放控制、自动布局、对齐辅助线
- **编辑增强**：撤销/重做、复制粘贴、批量操作、快捷键
- **右键菜单**：新增下属、调整岗位、绑定工具、删除等快捷操作

#### 6. 模板/Playbook 生态薄弱

**现状**：
- 有 Template 和 Playbook 两个概念，但内置模板少
- 没有社区分享机制

**对比**：
- Flowise：丰富的社区模板市场
- CrewAI：大量官方和社区 Crew 模板

**改进建议**：
- **内置丰富模板**：按场景分类（研发、营销、客服、内容创作、数据分析等）
- **模板市场**：支持一键导入/导出，社区分享
- **Playbook 市场**：可复用的工作流模板
- **模板评分与评论**：社区反馈机制

### 🟢 P2：进阶能力

#### 7. 多模型支持不透明

**现状**：
- 内置 agentType 有 sonnet/opus/haiku（Claude 系列），但模型配置不透明
- 用户无法选择和配置模型

**改进建议**：
- **模型配置界面**：支持配置多个 LLM 提供商（OpenAI、Anthropic、OpenRouter、本地模型等）
- **角色级模型选择**：每个角色可以指定使用哪个模型
- **模型路由**：根据任务类型、成本、速度自动选择模型
- **模型成本统计**：运行后展示各模型的 token 消耗和费用

#### 8. 测试与验证能力弱

**现状**：
- 只有 Schema 验证
- 没有运行前的模拟测试

**改进建议**：
- **试运行模式**：用模拟数据测试流程是否通顺，不实际调用 LLM
- **组织健康检查**：自动检测配置问题（孤立角色、循环依赖、缺少 Skill 等）
- **A/B 测试**：对比两种组织架构在同一任务上的表现
- **回归测试**：保存典型用例，每次修改后自动跑一遍

#### 9. 团队协作缺失

**现状**：
- 单用户桌面应用
- 没有版本控制和协作能力

**改进建议**：
- **版本控制**：组织配置的版本历史，支持回滚
- **变更审计**：谁在什么时候改了什么
- **多人协作**：支持多人同时编辑（后续版本，需要后端服务化）
- **权限管理**：管理员、编辑者、查看者等角色

#### 10. 文档与引导不足

**现状**：
- 新用户上手可能不知道怎么用

**改进建议**：
- **新手引导**：首次启动的交互式教程
- **示例项目**：内置几个完整的示例组织，用户可以直接运行体验
- **帮助文档**：内置文档面板，随时查看概念说明
- **最佳实践**：每种场景的推荐配置指南

## 四、落地路线图建议

### Phase 1：核心体验优化（1-2 个月）
1. 前端三段式布局重构（组件库 + 画布 + 属性面板）
2. 运行时可视化增强（节点高亮、消息流向）
3. 内置 10+ 场景模板（研发、营销、客服等）
4. Skill 元数据增强（版本、分类、schema）

### Phase 2：能力升级（2-3 个月）
1. 自然语言编排（Vibe Graphing）
2. 项目组/矩阵式组织支持
3. Trace 视图与性能分析
4. 模型配置界面与多模型支持

### Phase 3：生态与社区（3-6 个月）
1. 模板/Skill 市场
2. 试运行与测试能力
3. 版本控制与审计
4. 文档与最佳实践体系
