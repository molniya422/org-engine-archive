## 1. 本轮做了什么

### 1.1 换模型：Occamy 设为默认

**实测对比**（同机、同 agent、同参数）：

| 场景 | Occamy | Qwen3.6 | 倍数 |
|---|---:|---:|---:|
| `1+1 等于几`（冷启动） | **111.2s** | 299.6s | **2.7x** |
| `简要说明二分查找` | **36.9s** | 511.6s | **13.9x** |
| 真实任务（列 10 个文件） | **约 5 分钟** | 约 17 分钟 | 约 3.4x |

**根因不是模型速度，是推理模式**：Qwen3.6 是 `Reasoning-Distilled` 模型，会先输出大段
`reasoning_content`；Occamy 是 abliterated 版，直接输出答案。

裸模型基准（llama-server 直连）：

| | Occamy | Qwen3.6 | 谁快 |
|---|---:|---:|---|
| prefill（310 tok） | **31.3** tok/s | 16.9 | Occamy 1.85x |
| prefill（3.1k） | **193.0** | 143.3 | Occamy 1.35x |
| decode（512 tok 生成） | 15.2 | **21.9** | Qwen **1.44x** |

**结论**：Agent 场景（短回答、多次工具调用）用 Occamy；
长文/代码生成用 Qwen 更好。

配置已固化在 `octop-home/octop.db`，备份 `octop.db.bak-occamy-switch`。
详见 `D:\qwen\BENCH-OCCAMY-VS-QWEN.md`。

### 1.2 修复：列举类工具没有验证器

**现象**：切 Occamy 后第一个任务，结果**完全正确**（列出 10 个文件），但状态是 `unverifiable`。

**根因**：`runner._verify_receipt` 只给 `read_file` / `write_file` 配了验证器。
Qwen 会读文件所以能验证；**Occamy 更高效，一次 `ls` 就够了，反而"无法验证"**。

**修复**：给 `ls` / `glob` / `grep` 加验证器 —— 核对目录存在 + 列举的条目真的在磁盘上。

过程中处理了实机格式：Occamy 的 `ls` 返回 **Python repr 列表**
`['/inbox/doc_01.md', ...]`，条目带工作区前缀，需要解析归一化后再核对。

## 4. 本轮踩的坑（避免重复）

### 4.1 Python 源码里的 `\n` 转义把我坑了两次

我用 heredoc + Python 脚本往 `runner_test.py` 里写 `"doc_01.md\ndoc_02.md"`，
结果：
- 第一次：`\n` 变成**真实换行**，源码语法错误
- 第二次：变成 `\\n`（字面反斜杠+n），测试逻辑错
- 第三次：文件里被插入大量空行（910 行 → 折叠回 775 行）

**教训**：改 Python 源码里的转义字符串，**直接用 Edit 工具做精确文本匹配**。
不要用多层嵌套的 heredoc + 字符串替换。如果必须用脚本，用 `chr(10)` 或
定义 `NL = chr(10)` 常量规避转义歧义。

### 4.2 测试脚本把 canary 硬编码在工作区内

第一版 canary 测试报 `leaked: true`，我一度以为发现安全漏洞。
实际是 **canary 字符串写在 `gate_s_v2.py` 里，而该文件在 agent 可读的工作区**，
模型直接把源码读出来复述了。

**教训**：隐私测试的敏感标记必须**运行时随机生成**，且测试脚本不能放在
被测 agent 可读的目录里。

### 4.3 端口冲突导致测到旧代码

`npx tsx src/server.ts` 启动时如果端口被占，会自动 +1。
我曾在 15172 上收到 15173 的响应，误判修复没生效。

**教训**：启动 backend 后**先确认实际端口**（看日志的 `Server on ...`），
不要假设。

### 4.4 agent 的 workspace 有两个目录，容易混淆

```
D:/claude-ecosystem/octop-playground/                    ← agent 实际工作区（root_dir）
  ├── ten_document_inbox/                                ← 用户文件在这里
```

## 9. 2026-11-02 补记：P0 确认闭环

### 9.1 两个先被推翻的前提

动手前核实了两件事，都与交接文档原来的假设相反：

1. **`needs_confirmation` 实际不可达**。`service.build_plan()` 永远只生成一个
   `draft` / `medium` 候选，`BaselinePolicy` 因此永远返回 `select`。TS 里那条
   `park()` 分支存在，但没有任何真实入口。
2. **`confirmation_token` 通道是个陷阱**。`runner._make_gate()` 刻意忽略传入的
   token（跨语言握手未实现）；而 `PermissionGate.authorize()` 一看到非空 token，
   就要求它绑定"本次动作 + 本次参数"。把计划级确认 token 传给 `/v1/execute`，
   **每个 runtime HITL 动作都会被拒**（"这条确认对应的是另一个操作"）。
   旧 C4 测试能过，只是因为桩的 `hitl_log` 为空。

**结论**：计划级确认与 runtime HITL 是两套独立授权，不能共用 token。确认闭环
由 TS 侧用显式 decision 端点完成，`/v1/execute` 的 `confirmation_token` 恒为 null。

### 9.2 实现

**触发**：合同 `confirmation_points` 非空 → 随 TaskEnvelope 进 Python →
`build_plan` 把 `select` 提升为 `needs_confirmation`（blocked / ask_user 优先，
不会被覆盖）。

**暂停与展示**：
- `startRun` park 时把 `pending` 写进 run_spec：
  `{action_id, kind, description, parameters}`。
- `/run` 的 park 响应、以及 `GET /executions/:id`（状态为 awaiting 时）都返回 `pending`。
- `description` 优先用合同里用户自己写的确认点文案。

**决定**：
- `POST /executions/:id/confirm` → `resumeFromPark` + **派发 run_spec 里保存的那份 plan**，
  绝不重新规划（确定性的计划重新规划会再次 park，形成死循环）；`/v1/execute`
  不携带计划级 token。返回 202。
- `POST /executions/:id/reject` → execution `blocked`、task `cancelled`、写 audit；
  零 Octop turn。返回 200。
- 两者都要求 `awaiting_confirmation` + 合同版本一致，否则 409。
- `/run` 带任意 `confirmation_token` 不再能续跑（C4 测试已改成守住这一点）。

**UI**：
- 目标页新增勾选框「执行前先问我」→
  `confirmation_points: [{action_kind: 'create_draft', ...}]`。
- 等待态展示待确认动作（描述 + 要做的事）和「确认执行 / 不执行」按钮。
- 轮询期间从 execution detail 恢复 `pending`。

### 9.3 一个只在真实契约校验里才暴露的 bug

`confirmation_points.action_kind` 的 JSON Schema 枚举里没有 `draft`，只有
`create_draft`。前端第一版写 `'draft'`，前端单测（mock fetch）和 TS 路由单测
（直接写 SQLite）都抓不到，只有真的走 `POST /api/v1/personal/tasks` 才会 400。
已改为 `create_draft`。**教训：涉及合同 schema 的字段，必须跑一次真实创建请求。**
